# stt — NOTES

## 설계 (2026-11-23, skill-craft 절차형 경로)

### 방향
- 계기: 유튜브 분석 에이전트를 만들기 전에 STT 정리. 사용자 말 — "유튜브에서 자동 번역 퀄리티가 낮으니까 내용을 텍스트화할 때 사용하려고",
  "모델을 task 상황에 따라 자동으로 고르는 방식으로하고 모델 경로는 스킬에서 범용적으로 다룰수 있게하돼 초기경로는 지금 로컬에 있는 모델은 활용하는 방식으로"
  (사용자는 "TTS 스킬"이라고 했지만 대화 전체가 음성→글이라 STT로 만듦 — `가정:`, 보고에 냄)
- 하는 일: 파일 → 작업에 맞는 로컬 엔진 자동 선택 → 받아 적은 글·구간·자막 파일.
- 끝났다: stdout `ok: true` + 마지막 구간 `end` ≈ `audio_s`.

### 만든 과정 (단계 ↔ 출처)
| 단계 | 출처 |
|---|---|

## 색인 (현재 유효)

  제목으로, 맥락이 비면 제목·채널·설명으로. 이유: 사용자가 "파일이야 링크야"에 링크를 고름 — 내려받기 코드를 한 곳에 (유튜브 에이전트·화면이 같은 길),
  25분 영상 소리 23MB·11초(측정)라 따로 받을 이점이 없음. 버린 대안: 밖(유튜브 에이전트)에서 받아 파일로 넘김 — 내려받기가 두 곳. "공식 자막이 있으면
  STT 를 건너뛴다"는 유튜브 고유 판단이라 유튜브 분석 에이전트에 둔다. 측정(2026-11-24): 25:44 영어 주소 → 84초, 26:28 한국어 주소 → 108초 (화면 서버, 받기 포함).
- [D10] 결정: 엔진·CLI를 스킬 폴더에서 프로젝트 `side_projects/stt/` 패키지로 옮기고 서버(8773)·A2A·화면을 붙임. 스킬의 `scripts/`·`models.json`은 지움
  (같은 코드 두 벌 금지). 이유: 사용자 — "이거 스킬이기도하고 우리하듯이 A2A랑 화면까지 붙이는 그 작업도 됐나?", 화면은 "디자인 스킬 쓰고" → 시안 B(멀티트랙 테이프).
  화면 과정·평가 기록은 `stt/docs/history/2026-11-23_screen-design/`. 다시 볼 조건: 없음.
- [D9] 결정: `--live <ffmpeg 입력 | ->`. Silero VAD(faster-whisper 내장 ONNX, 청크마다 상태 유지)로 0.6초 침묵에서 끊어 바로 받아 적고 JSON 한 줄씩.
  들어온 소리는 녹음해 두고 끝나면 파일 방식으로 다시 받아 적어 최종본. 이유: 사용자 — "TTS 입력이 저런 파일 단위일수도있고 실시간 입력일수도 있지않겠냐는 말이야"
  (TTS라고 했지만 받아 적기 입력 이야기). 끊기 값은 고객센터 음성 에이전트(다른 프로젝트)의 VAD 모듈와 같게 (실제로 썼던 값). 최종본을 다시 만드는 이유는 D7
  (쉼 끊기 인식이 덜 정확). 버린 대안: ① 고객센터 에이전트 모듈을 import — 다른 프로젝트 경로에 묶임, 끊기 로직 60줄이라 엔진 안에 둠. ② 실시간 화자 분리 —
  DiariZen은 파일 단위, 최종본에서 붙임. 다시 볼 조건: 실시간 줄에 화자가 필요해질 때 / 마이크가 필요해질 때(→ 브라우저 화면에서 PCM을 `--live -`로).
  측정(2026-11-23): 영어 60초 실제 속도 — 발화 5, 지연(발화 끝 → 줄 출력) 평균 1.57초·최대 2.73초, 인식 평균 1.17초/발화. 한국어 5.7분 빠르게 — 발화 35, 2,027자
  (파일 방식 2,030자). 부정: 없는 소스·빈 입력 → `ok:false`·종료 1 / 같은 폴더 → 거절 / Ctrl+C → 들은 만큼(18초) 최종본까지 만듦.
- [D8] 결정: 조각 글을 문장 부호로 나누고, 글자 비율을 조각 안 말소리 시간(faster-whisper Silero VAD, 쉼 300ms 이상 제외)에 배분해 문장 시각 추정.
  `timing: estimated`로 표시. 이유: 사용자 — "긴 영상에서의 발화시간은 앞의 시간 계산해서 보정가능하지않나", "그거랑 … 넣으면 좋겠는데".
  측정(2026-11-23): 영어 4분 샘플에서 첫 네 단어가 같은 Whisper 구간과 대조 31문장, 시작 오차 평균 0.27초·최대 1.14초. 버린 대안: 쉼 무시한 단순 비율 — 쉼이 길면
  뒤 문장이 당겨짐 (측정 안 함). 다시 볼 조건: 단어 단위 시각이 필요할 때 (→ 정렬 모델).

  이유: 같은 5.7분 한국어에서 맞고 틀린 단어 9개로 대조 — 쉼 끊기 맞음 4·틀림 2, 쉼 끊기를 15초까지 묶기 4·2, 지금 방식(15초, 조용한 지점) 8·1 (2026-11-23,
  스크래치 `vadexp.py`). 추정 원인: 쉼 구간을 빼면서 앞뒤 음절이 잘림 (확인 안 함). 다시 볼 조건: 실시간 입력(마이크·라이브)처럼 끊어야만 하는 경우.

  붙는다. 이유: 사용자 — "이건 솔직히 기본기능 아닌가", "그러니까 지금 사실상 오디오를 일정 단위로 끊어서만 넣으면 된다는거 아니야? 내가말한 기본기능은 둘다 붙어있고".

  다운로드가 필요하고, 발화 단위 시각이면 링크에 충분. 다시 볼 조건: 단어 단위 시각이 필요해질 때(→ 정렬 모델).
- [D5] 결정: 조각 최대 15초. 이유: 같은 5.7분 한국어를 30·15·10초로 비교(2026-11-23, 참조 대본 없음 — 차이 구간을 눈으로 봄). 15초가 30초보다
  실제 단어를 더 맞힘(더덕권→저작권, 낯민→난민, 칠산율→출산율, 국제이명→국제입양), 10초는 새 오류(생성형→상상형). 대신 15초는 숫자를 한글로 풀어 씀
  (98%→구십팔 프로). 버린 대안: 30초 — 시각이 거칠고 단어 오류가 더 많음. 다시 볼 조건: 참조 대본이 있는 실제 유튜브로 CER을 잴 때 (표본 1개라 약한 근거).
- [D1] 결정: `prefer` 하나(정확도 순)에 조건(언어·모델 있음·환경·GPU 여유)을 걸러 첫 엔진. 이유: 사용자 "task 상황에 따라 자동으로" — 지금은 언어·GPU 상황에 따라
  갈린다 (D6 이후 task 갈래는 없음). 버린 대안: task별 엔진 목록. 다시 볼 조건: 상황마다 정확도 순서가 달라지는 측정이 나올 때.
- [D2] 결정: `stt.py`(표준 라이브러리) → `models.json`의 `python`으로 `engine_run.py`를 띄움. 이유: Qwen·Whisper(voice-eval)와 DiariZen(diarizen, torch 2.1)이
  다른 환경이고 기존 환경을 바꾸지 않는다(voice `AGENTS.md`). 버린 대안: 한 환경에 다 설치 — torch 버전 충돌. 다시 볼 조건: 한 환경으로 모일 때.
- [D3] 결정: text는 Qwen3-ASR (1.7B 받으면 1순위, 지금은 0.6B). 이유: 이 대화의 조사(오픈 ASR 리더보드·한국어 비교 블로그 — 인용) + 위 벤치에서 0.6B CER 0.0 vs turbo 0.008
  (합성음 8문장, 약한 근거). 버린 대안: 전부 Whisper — 주변 도구는 많지만 text 용도엔 필요 없음. 다시 볼 조건: 실제 유튜브 음성으로 두 엔진 CER을 재면.
- [D4] 결정: `HF_HUB_OFFLINE=1` 기본, `--allow-download`로만 받음. 이유: 받기는 용량·시간 비용 (skill-craft 대원칙 3). 다시 볼 조건: 없음.

- [F2] 입력: 같은 파일, task subtitle. 증상: `TypeError: open() got an unexpected keyword argument 'metadata_errors'` (av). 원인: voice-eval의 PyAV 버전과

- [F3] 입력: 유튜브 DHRm_2A2Qag 4분, `--num-speakers 2`. 증상: "화자 분리 실패". 원인: diarize.py가 `<이름>.n2.rttm`으로 저장. 조치: `<이름>*.rttm` 패턴. 상태: 해결.
